# QRPick Opportunity Pipeline PRD

상태: **CANONICAL / MVP FROZEN**  
기준일: 2026-07-17

## 1. 제품 최종 정의

> 공공·민간 MICE·행사 기회를 수집·우선순위화해 사람이 매주 실행할 영업기회를 제공하는 내부 매출지원 시스템

핵심 산출물은 자동 결정이 아니라 **근거와 미확인 사항이 포함된 사람의 주간 검토 순서**다.

## 2. 문제 정의

MICE·행사 사업 기회는 지원사업 포털, 행사 일정, 기관 홈페이지, G2B 조달 생애주기에 분산되어 있다. 사람이 매번 여러 소스를 확인하면 다음 문제가 생긴다.

- 같은 사업을 반복 확인하거나 중요한 변경·후속 단계를 놓친다.
- 행사명만으로 QRPick 적용 가능성과 실제 영업 경로를 혼동한다.
- 직접입찰, PCO/기획사 협력, 낙찰사 공급 제안의 시점이 다르지만 한 목록에서 구분하기 어렵다.
- 상세·첨부를 읽지 않은 추정이 자격 확정 또는 `GO`처럼 전달될 위험이 있다.
- 후보가 많아도 매주 실제로 행동할 3~5건으로 줄어들지 않는다.

## 3. 제품 목표

1. 공개 소스의 원본과 판정 근거를 추적 가능한 형태로 보존한다.
2. MICE·QRPick 관련성과 현실적인 영업 경로를 설명 가능한 규칙으로 분류한다.
3. 내부 후보 풀과 운영자 기본 출력 Top 30을 분리한다.
4. 사람이 Top 30을 Top 10 상세검토, Top 3~5 실제 행동으로 전환하게 한다.
5. 부분성공·인증 부재·잘림·미확인을 성공으로 숨기지 않는다.
6. 4주 실제 운영 데이터가 생기기 전에는 기능을 확장하지 않는다.

## 4. 1차 사용자

- QRPick·쇼다 대표 또는 영업 책임자
- 공공조달·파트너 영업을 함께 검토하는 내부 실무자
- 데이터 수집 상태와 오분류를 점검하는 파이프라인 운영자

외부 고객, 여러 회사, 자동 입찰 에이전트는 사용자가 아니다.

## 5. 핵심 사용자 시나리오

### 주간 영업 검토

1. 운영자가 배치 파이프라인을 실행한다.
2. manifest와 오류·부분성공 상태를 확인한다.
3. `unified-opportunity-top30.csv`를 우선 연다.
4. 근거·미확인·주/보조 경로를 보고 Top 10을 선택한다.
5. 상세·첨부·자격·예산·일정을 사람이 확인한다.
6. Top 3~5에 직접입찰 검토, 파트너 접촉 또는 낙찰사 접촉을 수행한다.
7. 결과와 미실행 사유를 운영 기록에 남긴다.

### 데이터 품질 검토

1. 전체 원장과 후보 CSV의 건수를 비교한다.
2. normalization error, duplicate candidate, truncation, source status를 확인한다.
3. 오탐·미탐을 기록하고 반복되는 결함만 규칙 수정 후보로 올린다.

## 6. 현재 MVP 자동 입력 범위

### 현재 MVP 소스

- 공개 지원사업: K-Startup, 기업마당, NIPA, KOCCA, SMTECH 등 upstream `ir-search` 공개 수집기
- 공개 MICE 행사: 구현·활성화된 공식/공공 행사 소스와 시설 일정
- 공공조달: data.go.kr 조달청 OpenAPI의 용역 사전규격, 입찰공고, 낙찰, 계약

### 소스 원칙

- 공개 페이지·공개 API·공개 다운로드만 사용한다.
- 로그인, CAPTCHA, 접근제한을 우회하지 않는다.
- 약관·robots·권한이 불명확한 소스는 HOLD한다.
- 상업 집계 사이트는 원 출처보다 낮은 discovery source다.
- registry 등록만 된 소스는 “수집 구현”으로 간주하지 않는다.
- 민간 기회 범위는 현재 구현된 공개 행사 신호에 한정되며 포괄적 민간 입찰 피드는 미구현이다.

제품 전체의 데이터 출처 체계와 구현 상태 구분은 11장을 따른다.

## 7. 기회 유형과 영업 경로

기회 유형은 지원·실증·행사·조달·후속 영업을 포함할 수 있으나, 모든 레코드가 즉시 영업기회인 것은 아니다.

| 경로 | 의미 | 자동 판정 한계 |
|---|---|---|
| `DIRECT_PRIME_BID` | QRPick·쇼다가 주계약자로 수행할 수 있는 범위의 상세검토 후보 | 자격·실적·첨부 미검증이면 입찰 가능 확정 아님 |
| `CONSORTIUM_BID` | 기획·연출·전문 영역과 공동수행이 현실적인 후보 | 공동수급 허용 여부 확인 필요 |
| `SUBCONTRACT_OR_SOLUTION_PARTNER` | PCO·기획사·입찰사에 등록·체크인·웹·데이터 등을 공급할 후보 | 상대 회사와 실제 역할 미확인 |
| `AWARD_WINNER_SALES` | 낙찰사 확정 후 시스템·운영 공급을 제안할 후보 | 공급사 미정과 공개 연락경로 확인 필요 |

복수 경로는 한 레코드에 보존한다. 운영 출력은 `primary_opportunity_route` 하나와 `secondary_opportunity_routes`를 함께 표시한다.

## 8. 자동 판정 안전 원칙

현재 런타임 분류는 키워드, 날짜, 구조화 필드, 설정값에 기반한 결정적 규칙이다. LLM/AI API를 사용하지 않는다.

규칙이 할 수 있는 일:

- 관련성 신호와 부정 신호 탐지
- 보수적 중복과 생애주기 연결
- 경로 후보, 검토 우선순위, 미확인 사항 생성
- Top 30 정렬

규칙이 해서는 안 되는 일:

- 첨부를 읽지 않고 자격·예산·과업을 확정
- `VERIFIED_ELIGIBLE`, `GO`, `ACTION_NOW` 자동 승격
- 연락처·담당자·실적을 추정
- 최종 입찰 또는 지원 결정을 대신함

AI 상세심사는 MVP 이후 조건부 검토 항목이며 현재 제품의 필수 구성요소가 아니다.

## 9. Top 30 기본 출력 원칙

- 전체 원장과 전체 후보는 삭제하지 않는다.
- 운영자 기본 출력은 `top_n=30`이다.
- `NO_ACTION`은 기본 출력과 all-candidates 영업 후보 파일에서 제외하되 조달 원장에는 보존한다.
- 직접입찰·파트너 중복은 한 행으로 통합한다.
- 정렬은 다음 순서다.
  1. `pre_notice_priority`
  2. 최근 공개일
  3. MICE 적합 신뢰도
  4. QRPick 기능 직접 근거
  5. 예산 확인 여부
  6. 공개 연락경로 확인 여부
- 현재 구현은 지원사업·MICE 행사·G2B 생애주기를 최종 출력에서만 경량 통합한다.
- 도메인 원점수는 비교하지 않고 행동 시급성, 사업 적합성, 매출 가능성, 접촉 가능성,
  정보 완성도, 기한 위험, 최근 공개일을 공통축으로 다시 평가한다.
- 도메인 할당량은 적용하지 않으며 Top 30 구성과 독점 원인을 summary에 표시한다.

## 10. Top 30에서 Top 5~10으로 전환

자동 Top 30은 사람의 시작점이다.

1. Top 30에서 상세·첨부 접근 가능성, 본공고 상태, 중복·철회 여부를 확인한다.
2. 자격, 예산, 일정, 수행범위, 공동수급·하도급 조건을 확인해 Top 10을 만든다.
3. 내부 수행역량과 접촉 대상을 확인해 Top 3~5 행동을 정한다.
4. 행동 후 회신·상담·견적·제안서·계약 또는 미실행 사유를 기록한다.

상세검토 전 P0/P1은 “우선 검토”일 뿐 “즉시 실행 확정”이 아니다.

## 11. 제품 경계와 데이터 소스

- 본 프로젝트는 MIT License 기반 `ir-search` 수집 기능을 활용한다.

  G2B 생애주기 연결, 영업경로 판정, 통합 Top 30 출력이다.
- 원본 프로젝트 자체를 QRPick 제품으로 표현하지 않는다.
- 원본 MIT License와 저작권 고지를 유지하고 QRPick 확장은 원본 영역 밖에서 구현한다.

### QRPick 맞춤 제품 경계

제품은 다음을 목적으로 한다.

> 공공·민간 MICE·행사 기회를 수집·우선순위화해 사람이 매주 실행할 영업기회를 제공하는 내부 매출지원 시스템

제품의 기본 결과는 전체 데이터 원장이 아니라 통합 Top 30이며,
사용자는 이 중 5~10건을 상세검토하고 3~5건에 실제 행동한다.

### 데이터 출처 체계

| 1뎁스 | 2뎁스 | 주요 활용 |
|---|---|---|
| 지원사업·실증 공고 | K-Startup, 기업마당, NIPA, KOCCA, SMTECH 등 | 직접지원, 실증, 확장사업, 컨소시엄, 판로 |
| MICE 행사·기관 | 전시컨벤션센터, CVB·관광기관, 협회·학회, MICE 플랫폼, 상담회 기관, 민간 행사 플랫폼 | 주최기관 제안, 시스템·운영 공급 |
| 나라장터 조달 | 사전규격, 입찰공고, 낙찰정보, 계약정보 | 직접입찰 검토, 파트너 영업, 낙찰사 영업, 반복사업 추적 |
| 민간·상업 영업기회 | PCO·기획사, 민간 주최사, 호텔·리조트, 기업행사, 지역관광 사업자 | 직접판매, 공동제안, 운영 일괄수주 |
| 내부·수동 데이터 | 기존 고객, 파트너·인맥, 상담·견적, 과거 행사, 수동 발견 기회 | 접촉 가능성, 재영업, 차년도 추적 |

각 데이터 출처는 다음 상태를 구분한다.

- `IMPLEMENTED`: 실제 자동 수집·정규화 구현
- `PARTIAL`: 일부 기관, 단계 또는 표본만 구현
- `MANUAL`: 수동 입력 또는 조사
- `PLANNED`: 제품 범위에는 포함되지만 MVP 미구현

현재 상태:

- 지원사업·실증 공고: `IMPLEMENTED` — 열거한 upstream 공개 수집기와 Phase-2 처리 기준
- MICE 행사·기관: `PARTIAL` — 활성화된 공식·공공 소스 중심이며 전체 기관·민간 플랫폼을 포괄하지 않음
- 나라장터 조달: `PARTIAL` — 4단계 collector는 구현됐지만 실행별 실제 입력 범위가 다르며,
  입찰·낙찰·계약이 smoke 표본인 경우 전수 데이터로 표현하지 않음
- 민간·상업 영업기회: `PLANNED` — 일부 공개 행사 신호 외 포괄 자동 수집 미구현
- 내부·수동 데이터: `MANUAL` — 기존 고객·인맥·상담 이력을 자동 수집 완료로 표현하지 않음

### 나라장터 생애주기

`사전규격 → 입찰공고 → 낙찰정보 → 계약정보 → 차년도 반복사업`

- 사전규격: 본공고 전 직접입찰 검토 및 기획사 선제영업
- 입찰공고: 직접입찰·컨소시엄·솔루션 공급 검토
- 낙찰정보: 낙찰사 대상 시스템·운영 공급 영업
- 계약정보: 실제 수행사 확인 및 차년도 반복사업 추적

### 기본 출력과 사용자 행동

전체 원장은 데이터 추적과 재분류를 위해 보존한다.
기본 사용자 화면·CSV는 통합 Top 30으로 제한한다.

Top 30:

- 전체 후보를 모두 보여주는 목록이 아니다.
- 지원·입찰 가능성을 확정하는 목록이 아니다.
- 사람이 이번 주 검토할 순서를 제시하는 목록이다.

운영 흐름:

`수집 → 통합 Top 30 → Top 10 상세검토 → Top 3~5 행동 → 결과 기록`

### 규칙 분류와 AI 분석의 경계

현재 MVP:

- API·공개 데이터 수집
- 구조화 필드 정규화
- 키워드·부정어·조합조건·시나리오 기반 분류
- 영업경로 및 다음 행동 추천

현재 비범위:

- 모든 RFP 전수 AI 검토
- 첨부파일 자동 파싱
- OCR
- 자동 GO/NO-GO
- 자동 입찰·제출

직접입찰 후보는 자격이 확정된 공고가 아니라
상세 공고와 첨부를 추가 검토할 가치가 있는 후보이다.

### 명시적 비범위

- 범용 조달 AI SaaS
- 다회사 멀티테넌트 서비스
- 자동 입찰·자동 지원·자동 제출
- 자동 GO/NO-GO
- CRM 전체 대체
- 제안서 자동 생성
- 웹 대시보드
- 모든 민간 영업정보 자동 수집
- 모든 RFP 전수 분석, 첨부 다운로드·파싱, OCR
- AI 상세심사·자동 담당자 탐색·자동 이메일
- 운영 검증 없는 신규 수집기 확대

| FR-09 | 미확인 사항과 권장 다음 행동 생성 |
| FR-10 | 운영자 Top 30과 전체 후보·전체 원장 분리 |
| FR-11 | 실행 manifest, 통계, 부분성공 상태 출력 |
| FR-12 | Windows 배치 실행과 네트워크 격리 단위 테스트 |

## 13. 비기능 요구사항

- **설명 가능성:** 모든 판정은 코드·설정·근거 필드로 재현 가능해야 한다.
- **추적성:** source, source_id, 원문 URL, raw file, collected_at, lifecycle basis를 유지한다.
- **보수성:** 불확실한 중복·자격·역할은 병합·확정하지 않는다.
- **격리:** 한 소스 실패가 다른 소스 결과를 삭제하지 않는다.
- **재현성:** 실행일, 입력 경로, 설정, 건수, 오류를 산출물로 남긴다.
- **보안:** API 키와 개인정보를 코드·로그·manifest·보고서에 노출하지 않는다.
- **호환성:** Windows 배치와 Excel용 UTF-8 BOM CSV를 지원한다.
- **운영부하:** 기본 사람이 읽는 목록은 30건을 넘지 않는다.

## 14. 데이터 추적성

원본은 수정하지 않는다. 정규화 레코드는 가능한 범위에서 다음을 유지한다.

- source/source_scope/source_id
- 원문 URL 또는 공식 상세 URL
- raw file 및 수집 시각
- source occurrences와 중복 근거
- lifecycle group/link basis
- 분류 이유, evidence, confidence
- blocking unknowns
- 실행 manifest와 stage/source별 상태

코드 스키마가 문서의 필드 목록보다 우선하며 문서와 코드가 다르면 drift로 기록한다.

## 15. 상태값과 근거 표시

- 수집: `OK`, `OK_EMPTY`, `OK_TRUNCATED`, `FILTERED_ALL`, `PARTIAL_EXPECTED`, `PARTIAL_UNEXPECTED`, `FAILED` 등
- 검토: `HIGH_PRIORITY`, `REVIEW`, `DETAIL_REVIEW`, `LOW_FIT`, `EXPIRED`, `UNKNOWN`
- 행동: `QUALIFICATION_CHECK`, `SALES_OUTREACH`, `WATCHLIST`, `NO_ACTION`, `CLOSED`
- 사전규격: `P0_DETAIL_REVIEW`, `P1_PARTNER_OUTREACH`, `P2_QUALIFICATION_RESEARCH`, `P3_WATCH`, `NO_ACTION`

상태만 출력하지 않고 이유, evidence, confidence, blocking unknowns, recommended action을 함께 표시한다. 서로 다른 파이프라인의 상태 체계는 현재 통합되지 않았으며 같은 의미로 간주하지 않는다.

## 16. 오류·부분성공 정책

- 가능한 소스는 계속 처리하고 실패 소스는 manifest에 남긴다.
- 인증키 부재의 구조 검증은 `PARTIAL_EXPECTED`일 수 있으나 사업 운영 성공으로 계산하지 않는다.
- truncation은 정상 완료가 아니라 범위 제한이 있는 결과다.
- HTTP 200이라도 구조·건수 불일치가 있으면 parsing error로 분류한다.
- 정규화 오류 레코드는 별도 파일에 보존한다.
- 무결성 실패, 데이터 손실, 비밀 노출 가능성은 운영 중단 결함이다.

## 17. 개인정보와 API 키

- 공개 업무 연락처만 보존하며 개인 연락처를 추정하지 않는다.
- 주민번호, 계좌, 비공개 개인정보를 보고서에 기록하지 않는다.
- API 키는 환경변수로만 주입한다.
- URL, 오류, request metadata, manifest에서 키를 redaction한다.
- 회사 프로필의 `INTERNAL_COMPANY_PROFILE_ONLY` 정보는 공식 자격판정에 사용하지 않는다.

## 18. 성과지표

주간 기록:

- Top 30 유효 건수
- 상세검토 건수
- 직접입찰 검토
- 파트너 접촉
- 낙찰사 접촉
- 회신
- 상담
- 견적
- 제안서
- 계약
- 오탐
- 미탐
- 미실행 사유

제품 성공은 수집 건수 증가가 아니라 **상위 후보가 실제 검토·접촉·견적·제안으로 전환되는지**로 판단한다.

## 19. MVP 완료 기준

기능 완료 기준:

- 필수 수집·정규화·중복·분류·생애주기·경로·Top 30·전체 원장·근거·권장 행동·manifest·테스트·배치가 실행된다.
- 원본과 판정 근거가 추적된다.
- 상세 미검증 후보가 `GO`/`ACTION_NOW`로 승격되지 않는다.
- Top 30은 중복 없이 30행 이하이며 all-candidates와 원장이 보존된다.
- 핵심 테스트가 모두 통과한다.

운영 완료 기준:

- 최소 4주간 주간 플레이북을 실행한다.
- 누락 없이 핵심 지표와 미실행 사유를 기록한다.
- 오탐·미탐과 실제 병목을 근거로 다음 투자 여부를 결정한다.

현재는 **기능 기반 MVP와 제품 전체 통합 출력이 구현된 상태이나 4주 운영 검증은 미완료**다.

## 20. 향후 기능 진입 조건

신규 기능은 “있으면 좋음”으로 시작하지 않는다. 다음을 모두 충족해야 검토 안건이 된다.

1. 4주 이상 실제 운영 기록이 있다.
2. 반복되는 문제와 손실이 지표로 확인된다.
3. 현행 수동 절차나 규칙 수정으로 해결되지 않는다.
4. 개인정보·약관·보안·운영비를 검토한다.
5. 성공 기준과 중단 기준을 사전에 정의한다.
6. 제품 책임자가 MVP 동결 해제를 명시적으로 승인한다.

AI 상세심사는 추가로 다음 조건을 모두 충족해야 한다.

- 주당 상세검토 후보 10건 이상
- RFP 독해 시간이 반복 병목으로 확인
- 추출 항목 표준화 완료
- AI 결과가 실제 영업·입찰 결정에 사용될 가능성 확인

## 22. 코드 부합성 감사 결론

- **과도 확장:** 넓은 source registry, 세 개의 분류/행동 taxonomy, 빈 dashboard/proposal 레이어는 확장 유혹이 있으므로 동결한다.
- **불필요한 복잡성:** 제품 전체 공통 모델 없이 도메인별 분류·리포트가 병렬로 존재한다. 통합 리팩터링은 실제 운영 병목이 확인될 때만 검토한다.
- **직접입찰 표현:** 코드 gate는 보수적이지만 `direct-bid-opportunities` 명칭은 확정처럼 읽힐 수 있다. 운영 문서에서는 “직접입찰 상세검토 후보”로 해석한다.
- **규칙과 AI:** 현재 구현은 규칙 기반이며 AI 런타임은 없다. 문서·UI에서 AI 판정으로 표현하지 않는다.
- **내부 풀과 기본 출력:** 도메인 원장은 그대로 유지하고 최종 단계의 경량 통합 원장과 제품 Top 30을 분리한다. `NO_ACTION`은 원장에만 보존한다.
- **행동 연결:** 권장 행동은 존재하지만 소유자·완료·결과 이력은 외부 운영 기록에 남겨야 한다. 현재 시스템은 CRM이 아니다.
